# 시간축: 출시일과 솔로 레이드 달력

"2주년 당시 메타"를 보려면 먼저 그때 **어떤 니케가 존재했고 어떤 솔로 레이드가
열려 있었는지**를 정확히 알아야 한다. 이 문서는 그 두 가지를 공지에서 복원하는
규칙과, 규칙이 닿지 못하는 곳을 적는다. 코드는 `build/releases.py`,
`build/soloraid.py`, 조회는 `timeline.py`.

모든 시각은 KST다. 공지가 "(UTC+9)"로 적기 때문이다. `nikke asof 2024-11-04`
처럼 날짜만 주면 **정오**로 본다. 아침 점검과 12:00 오픈이 끝난 뒤라서 "그날 열려
있던 것"을 묻는 질문에 그날 기준으로 답한다.

## 공지

| 채널 | 무엇이 있나 | 수집 |
|---|---|---|
| nikke-kr.com 공지사항·뉴스 | 2022-11 런칭 전부터 모든 정기 업데이트 공지 (본문 HTML) | `GetContentByLabel` → `GetContentInfoById` |
| 네이버 게임 라운지 공지 게시판 | 운영 공지: 솔로 레이드 중단·재오픈·연장·연기, 점검 연장 | 게시판 피드 API (본문 포함) |

두 채널은 업데이트 공지 본체를 공유하지 않는다. 공식 사이트에만 정기 업데이트
공지가 있고, 라운지에만 긴급 운영 공지가 있다. 그래서 둘 다 필요하다.

수집은 증분이다. 공지는 게시 후에 수정되기 때문에(제목에 "(9월 23일 공지 수정)"
이 붙는다) 매 실행마다 **새 공지, 제목이 바뀐 공지, 최근 45일 공지**를 다시 읽고,
내용이 실제로 바뀐 것만 저장한다. 라운지는 `updatedDate` 가 있어서 첫 페이지부터
새 것이 없는 페이지까지만 읽는다. `--full` 이면 전부 다시 읽는다.

## 출시일

### 규칙

업데이트 공지의 신규 니케 소개는 2022년부터 거의 같은 모양이다.

```
1. 신규 니케
1.1 SSR 니케 [길티 : 마이티 바니]
괴력에 첨단 슈트를 더한 ..., SSR 니케 [길티 : 마이티 바니]가 특수 모집에 합류합니다.
*특수 모집 기간: 2026년 9월 17일 서버 점검 종료 이후 ~ 2026년 10월 8일 4:59:59 (UTC+9)
```

1. 번호 붙은 제목(`1.`, `1.1`, `2-1.`)이 **주어**를 연다. 주어는 제목이 이름을 대는
   니케, 없으면 그 뒤 첫 소개 문장("SSR 니케 X가 … 합류합니다")의 니케다. 니케를
   대지 않는 제목은 주어를 비운다. 그래서 같은 섹션 뒤쪽의 "신년 특별 스텝업 모집
   기간"이 앞 니케에 붙지 않는다.
2. "…모집 기간:" 또는 "…획득 기간:" 줄의 날짜 범위가 주어의 모집 기간이다.
3. 섹션이 "신규 니케/신규 캐릭터/신규 한정 캐릭터"이거나 소개 문장이 합류·참전이면
   **데뷔**, "재합류"이거나 선택 모집이면 **재모집**이다.
4. 출시 시각 = 그 니케의 **가장 이른 데뷔 모집 시작**.
5. 신규 니케로 소개됐는데 모집 기간이 없으면(이벤트·로그인·해방 보상) 공지 제목의
   업데이트 날짜("4월 25일 업데이트 공지")를 쓴다.

"서버 점검 종료 이후"는 시각이 아니라 날짜만 알려준다. 그 날 00:00 으로 적고
`start_after_maintenance=1` 로 표시한다. 시각을 지어내지 않는다.

### 이름

공지 속 이름은 별칭 표(`unit_aliases.csv`)로만 풀린다. 추측하지 않는다.

- 게임 파일의 EN/KO/JA 이름
- 콜라보 니케의 풀네임: 게임 파일 설명문의 "풀네임은 스즈하라 사쿠라." 에서 자동 추출
- 풀네임을 끼운 변형: "레이 (가칭)" → "아야나미 레이 (가칭)", "퀸(마코토)" → "퀸(니지마 마코토)"
- `data/manual/unit_aliases.csv` 의 수동 별칭

**동명이인**이 실제로 있다. 사쿠라(282, 2023)와 사쿠라(836, 2025 콜라보)는 한·영·일
이름이 모두 같고, 라이(392)와 레이(831)는 영어로 둘 다 "Rei"다. 이런 이름은 어느
쪽으로도 풀지 않고, 공지가 쓰인 시점에 게임 데이터에 존재하던 니케가 하나뿐일 때만
그 니케로 본다. 그래도 둘이면 `release_unresolved.csv` 에 남는다.

### 알려진 공백

| 니케 | 이유 | 지금 쓰는 날짜 |
|---|---|---|
| 루피 : 윈터 쇼퍼, 네베, 앤 : 미라클 페어리 | 2022-12-08 업데이트 공지가 공식 사이트·라운지 어디에도 남아 있지 않다 | 데이터 파일 날짜 (12/08, 12/08, 12/15), 신뢰도 low |
| 길티, 신, 퀀시 | 모집이 아니라 [해방] 시스템으로 추가됐고 공지가 이름을 따옴표로만 적는다 | 데이터 파일 날짜 (2023-01-12, 실제 업데이트일과 같음), low |

정확한 날짜를 확인하면 `data/manual/release_overrides.csv` 에 사유와 함께 적는다.

### 런칭 로스터

어떤 공지도 소개한 적 없고, 게임 데이터 등재일이 글로벌 출시(2022-11-04) 이전인
니케는 **런칭 로스터**(`launch`, 신뢰도 medium)다. 공지 기록이 출시 이전부터 있다는
것이 확인될 때만 이렇게 판정한다. 현재 62명이다.

## 솔로 레이드 달력

업데이트 공지의 일정은 계획이다. 실제로는 이런 일이 있었다.

| 시즌 | 공지된 일정 | 실제 |
|---|---|---|
| 8 | 12/08 오픈 | 오픈 직전 연기 → 12/14 ~ 12/21 |
| 19 | 10/31 ~ 11/07 | 11/01 22:00 중단 → 11/08 재오픈 → 11/12 18:00 중단(챌린지 기록 초기화) → 11/13 12:00 재개, 11/17 05:00 까지 연장 |
| 26 | 06/19 ~ 06/26 | 06/20 00:00 중단 → 06/24 재오픈 → 06/26 00:00 재중단 → 07/03 ~ 07/10 |
| 28 | 08/21 ~ 08/28 | 08/26 17:00 ~ 21:00 중단(기록 초기화) → 09/01 까지 연장 |
| 38 | 06/18 ~ 06/25 | 06/23 04:59 중단 → 07/03 ~ 07/08 재오픈(기록 초기화) |

이 사실은 라운지 공지에만 있다. 패치노트만 읽으면 틀리고, enikk 만 읽어도 틀린다
(enikk 는 랭킹을 수집한 시각만 안다). 그래서 네 단계로 복원한다.

### 1. 이벤트

모든 공지에서 솔로 레이드 문장을 뽑는다. 업데이트 공지에서는 "솔로 레이드" 섹션
안의 문장만, 라운지의 솔로 레이드 공지에서는 전체를 본다.

| 이벤트 | 문장 예 |
|---|---|
| `open` | 솔로 레이드 시즌 41이 2026년 9월 24일 12:00:00에 오픈됩니다. + `*오픈 시간: A ~ B` |
| `reopen` | 솔로 레이드 시즌 38이 … 재오픈됩니다. / `✅ 솔로 레이드 재오픈 기간 - A ~ B` |
| `reschedule` | 솔로 레이드 시즌26의 진행 기간이 아래와 같이 변경됩니다. `└ A ~ B` |
| `suspend` | … 22:00부터 일시적으로 중단될 예정입니다. / `✔️ 일시 중단 기간 - A ~ B` |
| `extend` | `✔️ 연장 기간 - A ~ B` / `✔️ 진행 기간 연장 - 11/17(일) 5:00까지` |
| `postpone` | 12월 8일(금) 오픈 예정이었던 솔로 레이드가 연기될 예정입니다. |
| `reset` | 챌린지 모드의 기록이 초기화되며 |
| `issue` | 일정을 바꾸지 않는 솔로 레이드 공지 (이상 현상 확인, 비정상 데이터 처리 결과) |

라운지 공지는 필드 이름과 값을 다른 줄에 쓴다(`✔️ 중단 일시` / `- 6/23(화) 4:59:59`).
이 둘을 한 줄로 합쳐서 읽는다. 같은 중단이 문장과 필드로 두 번 적히면 재개 시각이
있는 쪽을 쓴다. 날짜만 있는 "일시" 필드가 같은 날의 정확한 시각과 겹치면 버린다.

### 2. 시즌으로 묶기

오픈 계열 이벤트를 시간순으로 놓고, 다음 경우에만 앞 시즌에 붙인다.

- 같은 시즌 번호가 적혀 있다
- 재오픈이거나 일정 변경이다
- 앞 시즌 기간과 겹친다 (같은 일정의 재공지, 수정)
- 사이에 중단·연기가 있고 앞 시즌 종료 후 10일 안에 열린다

26시즌부터는 공지에 번호가 있다. 번호가 없는 1–25시즌은 복원한 운영 구간과
enikk 의 수집 시각을 맞춰 번호를 붙이고, enikk 에도 없으면 번호 있는 이웃에서 센다.
번호가 겹치거나 시간 순서가 뒤집히면 빌드 결과의 `problems` 에 나온다.

### 3. 운영 구간

시즌의 이벤트를 시간순으로 재생한다. 오픈은 구간을 열고, 중단은 닫는다(재개
시각이 있으면 거기서 다시 연다). 연장은 끝을 늦추고, 연기는 그 전에 공지됐지만
아직 시작하지 않은 오픈을 취소한다. 결과가 `soloraid_periods.csv` 다.
`end_reason` 은 `scheduled`(예정대로 종료), `suspended`, `extended`, `superseded`
(새 일정으로 교체) 중 하나다.

### 4. enikk 와 대조

enikk 는 시즌마다 서버별 랭킹을 거의 매시간 수집한다. 그 첫 수집과 마지막 수집이
"이 기간에 실제로 플레이가 있었다"는 증거다. 수집은 오픈 하루이틀 뒤에 시작해
종료 며칠 뒤에 끝나곤 하므로, 일정의 출처가 아니라 검증 수단으로만 쓴다.

`soloraid_seasons.csv` 의 `checks` 에 남는 것:

| 표시 | 뜻 |
|---|---|
| `enikk_after_periods` | enikk 가 마지막 구간 종료 5일 뒤에도 수집했다 (공지되지 않은 연장?) |
| `enikk_before_periods` | enikk 가 첫 구간 시작 전에 수집했다 (번호가 어긋났을 수 있음) |
| `enikk_outside_periods` | enikk 의 마지막 수집이 어느 구간에도 속하지 않는다 |
| `element_mismatch` / `weakness_mismatch` | 공지의 보스 속성과 enikk 가 다르다 |
| `no_notice` | enikk 는 알지만 공지가 아직 없다 (예: 공개 전인 다음 시즌) |
| `no_enikk` | 공지는 있는데 enikk 에 없다 |
| `boss_unnamed` | enikk 의 보스 이름이 숫자열뿐이다 (5시즌) |

지금 데이터에서는 42시즌(`no_notice`, 아직 공지 전)과 5시즌(`boss_unnamed`)만 남는다.

## 새 패치가 나오면

`nikke refresh`(또는 주 2회 CI)가 전부 처리한다.

1. 게임 파일 미러에 신캐가 추가되면 로스터에 행이 생기고, nikke-utils 가 아직
   모르는 속성은 enikk 로 채운다.
2. 업데이트 공지가 올라오면 신캐의 출시 시각, 모집 기간, 다음 솔로 레이드 시즌이
   들어간다.
3. 라운지에 중단·재오픈 공지가 올라오면 그 시즌의 운영 구간이 다시 계산된다.
4. enikk 가 새 시즌을 수집하기 시작하면 교차검증이 갱신된다.

사람이 볼 곳은 세 군데뿐이다: `release_unresolved.csv`(못 푼 이름),
`soloraid_seasons.csv` 의 `checks`, 그리고 빌드 결과의 `problems`.
